# 产品 Spec: 警报强制中断能力

> 本 Spec 说明「警报强制中断」要解决什么问题、做到什么程度，以及产品行为与系统契约的约束；实现细节（类、方法、DDL、测试切分）留给技术设计。

## 0. 结论摘要（供评审快速阅读）

| 项 | 结论 |
|---|---|
| 一句话 | 在 AMS 警报详情中增加「强制中断」，使具备中断权限的使用者可以在警报仍处理中（Process）时填写原因并二次确认后终止警报，而无须等回应人数达标。 |
| 影响角色 | 具备中断权限的使用者（新增使用者主档字段控制）；普通通知人员/ACK 人员行为不变。 |
| 影响范围 | 使用者主档（新增权限字段）、警报详情页（按钮/二次确认/状态展示）、警报状态机（新增 Terminated）、通知与调度（停止升级/失败重送）、交易履历与报表（AVPA007/AVPA004/AVPA013）、功能树（新增作业入口）。 |
| 单仓闭环 | 是，仅 DawnGuoDev/CX-AMS-1123（基线 release）。 |
| 需求打标 | **B 类（AI 辅助编程）**，1 个 WARN（safety），其余 6 维 PASS；见附录 A。 |
| 阻塞技术设计的未决项 | 无。3 个待确认项均给出默认方案，只影响字段名/文案/上限参数。 |

# 1. 背景与目标

## 1.1 背景

AMS 现有警报生命周期只有三条结束路径：当前层级回复人数达到「需要回应的人数」即 `Completed`；层级逾时且已无下一层时 `NoNextLevel`；以及人工 ACK 累计达标。业务上存在必须提前终止警报的场景，例如：机台已修复且无需原流程人员回复、警报属于误触发、事件配置错误导致警报持续升级、上游条件已不成立但流程仍按间隔升级并重送邮件。

现状下只能：

1. 等待所有层级走完直至 `NoNextLevel`，期间持续发邮件、升级、失败重送；
2. 或请各层级通知人员逐一 ACK 以触发 `Completed`，这与「强制中断」的业务语义不同，也没有可追溯的中断原因。

缺少一条可控、可授权、可追溯的中断通道，会造成无效通知干扰、报表口径失真（处理中堆积）与操作责任不清。

代码证据：
- `backend/src/main/java/com/changxin/ams/AlarmEngine.java` 中 `action()` 仅支持 `ack`，其它动作抛 `API 不存在/未知警报操作`；`close()` 仅写 `Completed`/`NoNextLevel`。
- `tick()` 只遍历 `STATUS=Process` 的警报做升级、失败重送、达标关闭，没有终止分支。
- `AlarmEngine.enrich()` 只输出 `CAN_ACK`，没有可操作权限标识。
- `metadata.json` 的 `SBRM_USER` 无任何授权/权限字段；`seed.json` 的 `functions` 无中断作业入口。
- `Reports.definition()` 对 AVPA004/AVPA007 直接复用列定义与 `STATUS` 文本查询，AVPA013 `summary()` 只统计 `Process`。
- 前端状态样式已预置 `.tag.Terminated` 与中立灰（`frontend/src/style.css`），多语词典已含「警报强制中断作业 / 强制中断处理中的警报，无需达到回应人数」等词条（`frontend/src/legacy-i18n.js`），但没有任何页面或接口使用它们——说明该能力在设计系统中预留、尚未实现。

## 1.2 目标

| 目标 | 衡量方式 | 目标值 / 判断标准 |
|---|---|---|
| 授权者可中断处理中警报 | 有权限账号在详情页看到可用「强制中断」按钮并成功中断 | 端到端成功 1 次即通过 |
| 中断必须可追溯 | AVPA007 可按 `TRX_TYPE=AlarmTerminate` 查到记录，含操作人/时间/原因 | 记录字段完整且与操作一致 |
| 中断后流程立即停止推进 | 中断后不再升级、不再失败重送、不再产生新待发送通知；队列中待发通知变为 `Skipped` | 观察 ≥2 个调度周期（默认 2s/次）状态不变 |
| 权限与状态边界清晰 | 无权限、非 Process、历史只读、重复提交均被拒绝且有明确提示 | 拒绝分支逐项验证 |
| 报表口径可区分 | AVPA013 不再计数已中断警报；AVPA004/AVPA007 可通过状态/交易类型区分 | 查询结果符合口径 |

## 1.3 不做什么（非目标）

- 不做「撤销中断 / 恢复为 Process」；中断为终态，不可逆。
- 不做批量中断（列表多选批量终止）。
- 不做审批流（二级审批、主管签核、工单联动）。
- 不新增通知渠道（短信/IM/语音），不新增「中断广播」类新通知。
- 不改造既有权限模型（不引入 RBAC 角色表/权限矩阵；仅在用户主档增加一个布尔类授权字段）。
- 不改动 ACK 语义（ACK 仍是「回应」而非「中断」）；不改动升级间隔、ACK 人数、失败重送配置结构。
- 不新增数据库表/外部中间件；沿用 H2 JSON 快照存储。
- 不改变历史交易详情的只读语义（历史详情不得出现可执行的中断按钮）。

# 2. 用户与场景

| 用户 / 角色 | 使用场景 | 当前痛点 | 期望结果 |
|---|---|---|---|
| 值班主管 / 设备主管（被授予中断权限） | 机台已修复或确认误报，希望立即结束警报流程 | 只能逐层找人 ACK，或等所有层级逾时失败 | 在详情页一键发起中断，填写原因并确认后立即结束 |
| 值班工程师（无中断权限） | 打开警报详情查看进展 | 看到按钮会误以为可操作；看不到则不知为何不可操作 | 看到禁用按钮与「无中断权限」说明，能联系有权限者处理 |
| 系统 / 通知收件人 | 中断发生时仍有 Pending 通知或正处于升级计时 | 中断后仍收到邮件、仍有升级 | 不再收到新邮件，调度不再升级/重送 |
| 报表使用者 / 稽核 | 追查「谁在何时因何中断了警报」 | 无法区分完成与中断，也不能定位责任人 | AVPA004/AVPA007 可按状态、交易类型筛选并查看原因 |

主流程（用户路径）：

1. 有权限用户登录（用户主档开启中断权限）→ 打开警报列表或待确认列表 → 进入「警报详情」。
2. 系统在详情中展示「强制中断」按钮（Process 且本人有权限时可用）。
3. 用户点击 → 弹出二次确认对话框：展示警报识别码/标题等确认信息、中断不可逆风险提示、必填「中断原因」。
4. 用户填写原因并点击「确认中断」→ 系统在服务端再次校验权限、状态、原因后执行中断。
5. 系统返回成功；详情刷新为 `Terminated`，展示「已中断」状态、中断人、中断时间、中断原因，按钮变为不可用。
6. 用户可在交易履历页签看到 `AlarmTerminate` 记录；在 AVPA007 中可按交易类型查询到该记录。

异常/回退路径：
- 提交瞬间警报已被 ACK 完成或被他人中断 → 提示「该警报已非处理中状态」并刷新详情为最新状态。
- 原因未填 / 全空白 → 提示必填，保留输入，可修改后重试。
- 无权限或被撤销权限 → 提示「您没有强制中断权限」，不执行任何写入。
- 网络或服务异常 → 提示系统错误，按钮恢复可点击，可重新提交；不发生部分写入（中断状态、层级关闭、交易写入在同一事务内）。

# 3. 功能需求

## REQ-001: 中断权限授予与判定

- **优先级**：P0
- **用户价值**：只有被授权的账号才能终止警报，避免越权干预与误操作。
- **需求描述**：使用者主档（SBRM_USER）新增「警报强制中断权限」字段，取值 `Y/N`，默认 `N`。该字段随用户主档的新增、修改、Excel 导入导出、隐藏/恢复一起保存与生效；服务端以当前登录用户该字段为唯一授权依据（前端按钮显隐不作为安全边界）。
- **验收标准**：
  - [ ] 当新增使用者未填写该字段时，系统保存为 `N`。
  - [ ] 当管理员将有权限值改为 `N` 并保存后，该账号下一次请求即被拒绝中断（无需重新登录，以服务端读取主档为准）。
  - [ ] 如果当前账号该字段为 `N`、空或用户已停用/隐藏，调用中断接口返回业务失败（HTTP 400，`ok:false`），且不产生任何状态、层级、通知、交易写入。
  - [ ] 在用户主档列表/编辑弹窗中可直接看到并维护该字段；主档履历记录该字段修改前后的值。

## REQ-002: 详情接口返回中断可操作性

- **优先级**：P0
- **用户价值**：前端能准确决定按钮是否可用、给出「无权限」还是「状态不允许」的提示。
- **需求描述**：`GET /api/alarms/:key` 响应在现有 `CAN_ACK` 之外新增 `CAN_TERMINATE`（布尔）：仅当「当前登录用户具备中断权限」**且**「警报 `STATUS=Process`」时为 `true`，其余一律 `false`。历史交易详情（带 `transaction` 参数）恒为 `false`。同时返回中断时的可展示数据（用于中断后详情展示）：中断状态、中断时间、中断原因、中断操作人（名称/代码）。
- **验收标准**：
  - [ ] 有权限用户打开 Process 警报 → `CAN_TERMINATE=true`。
  - [ ] 无权限用户打开同一警报 → `CAN_TERMINATE=false`，`CAN_ACK` 仍按既有规则计算。
  - [ ] 有权限用户打开 `Completed` / `NoNextLevel` / `Terminated` 警报 → `CAN_TERMINATE=false`。
  - [ ] 以 `?transaction=` 打开任一历史时点 → `CAN_TERMINATE=false`。
  - [ ] 中断后的详情可读取中断时间、原因与操作人姓名（操作人不存在时展示代码或「系统」）。

## REQ-003: 强制中断接口与校验

- **优先级**：P0
- **用户价值**：提供明确、幂等友好且可审计的中断能力。
- **需求描述**：新增 `POST /api/alarms/:key/terminate`，请求体 `{cmt}`（中断原因），响应 `{ok:true, alarm:<同详情结构>, terminated:true}`。服务端按顺序校验：API 形状 → 警报存在 → `STATUS=Process` → 当前用户具备中断权限 → 原因非空且不超上限。任一失败返回 `ok:false` + 明确 `message`（HTTP 400/404，与现有 `ApiException` 风格一致）。`:key` 支持 `ALARM_KEY` 或 `ALARM_ID`，与现有 ACK 接口保持 `ALARM_KEY` 主键行为一致（沿用现有 `store.mustFind` 语义，不做额外扩展）。
- **验收标准**：
  - [ ] 有权限用户对 Process 警报提交合法原因 → HTTP 200，`ok:true`、`terminated:true`，`alarm.STATUS=Terminated`。
  - [ ] 原因缺失、空字符串或全空白 → 400 并提示原因必填；状态不变。
  - [ ] 原因超过长度上限 → 400 并提示上限（默认与 ACK 备注对齐：见 4.2，按 500 字符实现）。
  - [ ] 无权限账号提交 → 400 并提示「您没有强制中断权限」；不产生写入。
  - [ ] 对已 `Completed` / `NoNextLevel` / `Terminated` 的警报再次提交 → 400 并提示「该警报已非处理中状态」；不重复写交易。
  - [ ] 不存在的 key → 404「警报不存在」。
  - [ ] 并发：两个有权限请求同一警报，只有一个成功；另一个得到「已非处理中状态」，全库只有 1 条 `AlarmTerminate` 交易。
  - [ ] 未登录请求 → 401（沿用统一鉴权）。

## REQ-004: 中断后的状态、层级与通知收敛

- **优先级**：P0
- **用户价值**：中断即为流程终点，不再打扰通知人、不再占用调度。
- **需求描述**：中断成功后在同一事务内：① 警报 `STATUS=Terminated`、写入 `COMPLETE_DT`（沿用现有关闭时点字段，作为结束时间）；② 记录 `TERMINATE_DT`、`TERMINATE_CMT`、`TERMINATE_USER_KEY`（可展示用，具体字段名技术设计确定，但语义必须可读回）；③ 当前层级 `alarm_levels.STATUS` 由 `Active` 置为 `Closed`（与 `close()` 行为一致，关闭所有仍在 Active 的层级）；④ 该警报所有 `RESULT=Pending` 的 `alarm_notifications` 置为 `RESULT=Skipped`，`MESSAGE` 说明「警报已中断，取消发送」，`SEND_DT` 写入处理时刻（若为空）；⑤ 写一条 `alarm_transactions`：`TRX_TYPE=AlarmTerminate`、`STATUS_BEFORE=Process`、`STATUS_AFTER=Terminated`、`USER_KEY`=操作人、`TRX_DT`=操作时刻、`NOTE`=中断原因。
- **验收标准**：
  - [ ] 中断后详情顶部状态徽标为 `Terminated`（展示文案「已中断」）。
  - [ ] 该警报不再出现在 AVPA013 即时汇总的 `ALARM_COUNT` 中。
  - [ ] 中断前处于 `Pending` 的通知在中断后（调度处理或中断同事务）变为 `Skipped`，且不会触发 SMTP 发送。
  - [ ] 中断前处于 `Fail` 且未达重送上限的通知，中断后不再产生新的重送队列记录。
  - [ ] 中断前层级尚未逾时的警报，在后续 ≥2 个调度周期内不再出现 `LevelUpgrade` / `AlarmFail` / `AlarmComplete` 交易。
  - [ ] 中断后该警报不再出现在「待我确认（ACK_LIST）」列表与 `GET /api/alarms/pending` 结果中（其现行查询条件即 `Process`，需回归验证仍成立）。
  - [ ] `alarm_acks` 历史记录不被删除，详情中仍可查看已发生的 ACK 与通知记录。
  - [ ] 中断事务失败（异常）时，上述 ①~⑤ 全部不落库，警报仍为 `Process`，前端得到错误提示。

## REQ-005: 详情页中断交互（含二次确认）

- **优先级**：P0
- **用户价值**：让有权者能安全、明确地完成不可逆操作；让无权者理解边界。
- **需求描述**：在「警报详情」弹窗主资讯页签的工具区新增中断操作：
  - 有权限且 `Process`：展示主危险按钮「强制中断」（`danger`）；点击弹出确认对话框，含：标题「确认强制中断警报？」、目标警报识别码与标题、不可逆风险提示（中断后不可恢复、当前层级关闭、不再发送通知与升级）、必填「中断原因」文本域（必填星号、占位提示、字数计数、上限提示）、按钮「取消」与「确认中断」。
  - 已有权限但状态非 `Process`：按钮禁用，旁边说明「仅处理中（Process）的警报可中断」。
  - 无权限且 `Process`：按钮禁用，说明「您没有强制中断权限，请联系具权限人员处理」。
  - 历史交易只读详情：不展示中断按钮。
  - 提交中：按钮 `loading`，对话框不可重复提交；失败保留对话框与已输入原因并展示错误；成功关闭对话框、刷新详情、全局提示「警报已中断」，并通知外层列表刷新。
- **验收标准**：
  - [ ] 有权限 + Process：按钮可见可用，点击后出现二次确认对话框。
  - [ ] 确认对话框未填原因时「确认中断」不可提交（校验提示可见）。
  - [ ] 点击「取消」或关闭对话框：不发请求、状态不变、原因清空。
  - [ ] 确认成功后：对话框关闭、详情状态为「已中断」、显示中断人/时间/原因，按钮变为禁用。
  - [ ] 无权限账号不出现可点击的中断入口（禁用态必须带原因说明，不能静默隐藏导致困惑；如最终选择隐藏，需保留至少一处「无权限」说明）。
  - [ ] 历史交易详情页签无中断按钮。
  - [ ] 前端不把按钮状态作为安全边界：绕过前端直接调用接口时仍被服务端拒绝。

## REQ-006: 中断信息展示与报表口径

- **优先级**：P1
- **用户价值**：稽核与复盘可区分「正常完成」「层级耗尽失败」与「强制中断」。
- **需求描述**：
  - 详情页展示中断信息（中断时间、操作人、中断原因），在交易履历中可见 `AlarmTerminate` 记录及 `NOTE`。
  - AVPA007 历史查询：`TRX_TYPE=AlarmTerminate` 可作为条件筛选值，`STATUS=Terminated` 可查；该记录的「状态」列取交易后状态 `Terminated`。
  - AVPA004 处理查询：`STATUS` 条件支持 `Terminated`；列表状态列显示 `Terminated`；`COMPLETE_DT` 有值。
  - AVPA013 即时汇总：仅统计 `Process`，中断后不再计入（沿用现行 `summary()` 逻辑即可满足，需回归防止误改）。
  - 状态枚举下拉（`options.alarmStatus`）增加 `Terminated`，保持现有顺序追加。
- **验收标准**：
  - [ ] AVPA007 按 `TRX_TYPE=AlarmTerminate` 查询，返回记录含警报识别码、序号、操作时间、备注=中断原因，点开交易详情为只读且状态为 `Terminated`。
  - [ ] AVPA007 按 `STATUS=Terminated` 查询可返回该警报。
  - [ ] AVPA004 按 `STATUS=Terminated` 查询可返回该警报，`COMPLETE_DT` 非空。
  - [ ] AVPA013 中断后刷新，该厂别/子系统/机台的 `ALARM_COUNT` 相应减少。
  - [ ] 全部既有状态（Process/Completed/NoNextLevel）查询结果与改造前一致（回归）。

## REQ-007: 功能树与作业入口

- **优先级**：P2

关键文案（建议值，三语词条已存在，技术设计可按词典复用）：

- 按钮：`强制中断`；对话框标题：`确认强制中断警报？`
- 风险提示：`中断后警报将结束且无法恢复；当前层级将关闭，不再发送通知、升级或失败重送。`
- 原因标签：`中断原因`（必填）；占位：`请填写中断原因（例如：机台已修复、误报、事件配置错误）`

- 无权限说明：`您没有强制中断权限，请联系具权限人员处理。`
- 状态不允许说明：`仅处理中（Process）的警报可中断。`
- 状态展示：`Terminated / 已中断`（沿用 `.tag.Terminated` 中立灰色）

## 4.2 字段与校验

| 字段 | 类型 | 是否必填 | 默认值 | 校验规则 | 展示 / 使用位置 |
|---|---|---|---|---|---|
| 警报强制中断权限（建议 `CAN_TERMINATE`） | 复选框（Y/N） | 否 | `N` | 取值仅 `Y`/`N`；非 `Y` 一律视为无权限 | SBRM_USER 列表与编辑、Excel 导入导出、主档履历、服务端鉴权 |
| 中断原因 `cmt` | 多行文本 | 是 | 无 | 去首尾空白后非空；长度上限与 ACK 备注对齐（默认 500 字符）；超限拒绝 | 二次确认对话框、交易记录 `NOTE`、详情「中断原因」 |
| 状态 `STATUS` 枚举 | 枚举 | — | — | 在 `Process/Completed/NoNextLevel` 基础追加 `Terminated` | 详情徽标、报表查询条件与列、状态选项 |
| `CAN_TERMINATE`（详情响应字段） | 布尔 | — | `false` | 由服务端计算，前端只读 | 详情接口、前端按钮控制 |
| `TERMINATE_DT` / `TERMINATE_USER_KEY` / `TERMINATE_CMT` | 时间 / 关联 / 文本 | — | 空 | 仅中断时写入，之后不可变 | 详情展示、报表可选列（默认不改报表列，只改状态口径） |

说明：现有代码未对 ACK 备注做长度校验，因此「按 ACK 备注对齐」在实现上以新增同一常量同时用于 ACK 与中断为准（默认 500）；若产品最终定为无上限，仅需去掉该常量，技术路径不变。

## 4.3 状态与流转

| 操作 | 前置状态 | 目标状态 | 用户可见反馈 |
|---|---|---|---|
| ACK 达标 / 层级达标 | Process | Completed | 现状不变 |
| 层级逾时且无下一层 | Process | NoNextLevel | 现状不变 |
| **强制中断（有权限 + 原因）** | **Process** | **Terminated** | **提示「警报已中断」，详情显示已中断与中断人/时间/原因** |
| 强制中断（无权限） | Process | Process（不变） | 「您没有强制中断权限」 |
| 强制中断（状态非 Process） | Completed / NoNextLevel / Terminated | 不变 | 「该警报已非处理中状态」 |
| 强制中断（原因不合法） | Process | Process（不变） | 原因必填 / 超长提示 |
| 撤销中断 | Terminated | 不支持 | 无入口（非目标） |

状态机约束：`Terminated` 为终态，无任何出边；调度器、ACK、自动完成、升级、重送均不得作用于非 `Process` 警报。

# 5. 约束与风险

## 5.1 非功能要求

| 类别 | 要求 | 验收方法 |
|---|---|---|
| 一致性 / 事务 | 状态、层级关闭、Pending→Skipped、交易写入在同一 `store.write` 事务内完成；失败整体回滚 | 构造异常（如交易写入前抛错）验证库状态 |
| 并发 | 同一警报并发中断仅 1 次成功；不得出现 2 条 `AlarmTerminate` | 并发接口测试 |
| 权限 | 以服务端主档字段为唯一依据；不接受前端传入的权限标记；所有拒绝分支不产生副作用 | 越权接口测试（直接调 API） |
| 审计 | `alarm_transactions` 记录操作人、时间、原因；`SKIPPED` 通知保留原通知对象与发送结果 | 数据断言 |
| 兼容 | 现有 3 个状态与所有既有接口行为不变；旧用户数据无该字段时按 `N`；既有 AVPA004/007/013 结果回归一致 | 回归测试（后端集成 + 既有 E2E 用例） |
| 可观测 | 中断失败可通过现有统一错误响应定位；不输出敏感信息 | 日志/响应检查 |
| 性能 | 中断接口不引入外部调用（不发 SMTP）；单次响应在本地 MVP 量级 < 1s | 接口耗时断言（可宽松） |
| 国际化 | 新文案复用既有三语词典词条，缺失词条补齐 | 切换语言检查 |

## 5.2 风险与待确认

| 类型 | 描述 | 影响 | 处理方式 |
|---|---|---|---|
| 风险 | 中断是终态且不可撤销，误操作会造成警报记录提前结束 | 业务记录不完整 | 二次确认 + 必填原因 + 权限字段；报表保留完整履历 |
| 风险 | 中断与 SMTP 正在发送存在竞态：派发流程在锁外向 SMTP 发送，失败/中断可能同时发生 | 中断瞬间仍可能收到一封邮件 | 中断后置 `Skipped` 仅影响未发送；已发出的邮件不回撤（非目标）。在 Spec 明确告知，不承诺「绝对零邮件」 |
| 风险 | `Skipped` 通知若沿用现派发逻辑需确保不被判为 `Success` 或 `Fail` 重试 | 可能出现中断后仍重发 | 现 `tick()` 只重试 `Fail` 且只遍历 `Process`，应当天然满足；需测试锁定 |
| 风险 | 权限字段放在用户主档，单用户多场景授权粒度仍粗（全部厂别/事件） | 无法按厂别限制中断权 | 本次接受；粒度细分列为后续需求（非目标：不改造权限模型） |
| 待确认（默认：`CAN_TERMINATE`，授予 U001 等主管账号） | 中断权限字段命名与首授予账号 | 仅字段名/数据初始化 | 默认字段 `CAN_TERMINATE`，默认 `N`，种子数据至少 1 个演示账号置 `Y`；命名若定为 `IS_ALARM_TERMINATE` 仅参数级改动 |
| 待确认（默认：不发送） | 中断时是否向已收件人反向发送「警报已中断」通知 | 增加通知渠道/模板/新交易 | 默认不发；仅更新 `Skipped` 与履历；如需再做独立需求 |
| 待确认（默认：与 ACK 备注对齐，500 字符） | 中断原因长度上限 | 校验常量 | 默认新增共用常量 `COMMENT_MAX=500`；产品可调 |

> 上述 3 项均为参数级/文案级选择，不改变修改文件集合或架构，**不阻塞技术设计**；技术设计可按默认方案推进，并在实现中保留可调整常量。
