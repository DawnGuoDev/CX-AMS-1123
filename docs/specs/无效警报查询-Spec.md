# 产品 Spec: AMS DA｜无效警报查询 V2

> 本需求为已有需求「AMS DA｜无效警报查询」(task-yf09n597nk5nlztfzf6l) 的复刻 V2，内容一致，重新走典型研发流程。
> Spec 只约束产品行为、用户体验与系统契约；表结构、类设计等实现细节归入技术设计。

---

# 1. 背景与目标

## 1.1 背景

AMS（警报管理系统）在接收到上游 / 测试触发的警讯后，需依「厂别 + 子系统 + 机台 + 警报代码」四要素匹配警报通知设定，再走事件层级发送。当一笔警讯**未能成功产生有效警报**时（如厂别未设定、找不到对应事件、重复触发被忽略等），当前系统仅在触发接口返回一次 `422` 与中文原因（见 `AlarmEngine.invalid(...)`），**不落库、不保留历史**。

由此带来的问题：

- 运维 / 配置人员事后无法回答“某时间段内有哪些警讯没有变成警报、为什么没发出去”。
- 配置缺漏（未设定机台、事件停用、层级 1 无人等）只能靠当场复现，无法按时间区间排查和统计。
- 旧 Node 版本曾有“无效告警报表”，迁移 Java/Vue 时被一并删除（见 `README.md`、`docs/MANUAL_ALIGNMENT.md`），本需求在现行 Java/Vue 架构上以既有报表范式恢复该查询能力。

受影响用户：负责报警配置与值班排查的 AMS 运维 / 工程师（系统现有登录使用者，无新增角色）。

## 1.2 目标

| 目标 | 衡量方式 | 目标值 / 判断标准 |
|------|----------|-------------------|
| 无效警讯可留存 | 触发一笔未成功产生警报的警讯后可被查询到 | 每次 `invalid` 都生成 1 条带时间戳与原因的无效警报记录 |
| 按时间区间查询 | 用户用起止时间过滤 | 仅返回时间落在区间内的记录；边界包含端点 |
| 原因可解释 | 每条记录展示失效原因 | 原因文案与触发接口返回的 `message` 一致，可定位到四要素与匹配阶段 |
| 与现有报表体验一致 | 复用条件查询 + 表格 + 汇出 | 入口、条件弹窗、列过滤、排序、分页、Excel 汇出与 AVPA004/007 一致 |
| 不影响既有触发与发送链路 | 回归现有警报流程 | 成功触发、BYPASS、有效警报查询/汇出行为保持不变 |

## 1.3 不做什么

- 不恢复旧版被删除的人员群组、事件群组、多通道、机况/机型抑制、SQL 触发、独立强制中断等其它模块，仅做“无效警报查询”。
- 不改变触发接口的成功/失败语义与 HTTP 状态码（失败仍返回 `422`，不因此改为成功）。
- 不做无效警报的重发、补登、编辑、删除或 ACK；它是只读查询数据。
- 不做统计图表 / 仪表盘卡片 / 定时邮件报送（P2 范围外，后续可迭代）。
- 不回填历史：上线前未落库的失败触发无法追溯，仅统计上线后新产生的记录。
- 不引入新的通知通道、外部中间件或第三方服务。

# 2. 用户与场景

| 用户 / 角色 | 使用场景 | 当前痛点 | 期望结果 |
|-------------|----------|----------|----------|
| AMS 运维 / 值班工程师 | 报警未发出后，按时间段排查“哪些警讯失效、卡在哪一步” | 失效只在触发瞬间返回，事后无痕可查 | 打开无效警报查询，按时间区间看到失败明细与原因 |
| 报警配置人员 | 核对厂别/子系统/机台/事件/层级配置是否有缺口 | 无法快速发现“未设定机台/层级1无人”等配置缺漏 | 通过原因分类与四要素字段定位需补齐的配置 |
| 管理人员 | 导出某时间段无效警报清单做线下分析 | 无数据可导 | 一键汇出与画面一致的 Excel |

用户主路径：
1. 登录后从侧栏「查询报表」分组进入「无效警报查询」。
2. 点击「查询」打开条件弹窗，勾选时间区间（资料时间，介于起—止，精确到秒），可选叠加厂别/子系统/机台/警报代码/原因等条件。
3. 提交后表格按时间倒序展示无效警报记录。
4. 需要时用列过滤/排序二次收敛，或点击「汇出」导出当前画面结果。
5. 据原因与四要素去对应主档修正配置后，到「测试告警触发」复验。

异常 / 边界路径：区间内无记录显示空态；未设区间直接查询的处理见 4.1；触发失败时除原有提示外，记录已在后台留存，无需用户额外操作。

# 3. 功能需求

## REQ-001: 无效警讯落库留存

- **优先级**：P2
- **用户价值**：让“没发出去的警讯”事后可查、可追责、可定位配置缺口。
- **需求描述**：当一笔警讯经触发校验后**未能成功产生有效警报**时（即现行 `AlarmEngine.invalid(...)` 各分支），系统在返回原有失败结果的同时，持久化一条无效警报记录，至少包含：发生时间、厂别/子系统/机台/警报代码（按入参原样留存，含可能为空或不存在的代码）、警报标题/内容（如有）、失效原因、资料取得方式（Mock/Test，与有效警报一致）。
- **覆盖的失效原因（与现行触发校验一一对应，文案保持一致）**：
  - 未设定厂别
  - 未设定子系统
  - 未设定机台
  - 找不到事件（无匹配的警报通知设定，或绑定事件不存在/未启用）
  - 警报设定未启用
  - 忽略相同警报（重复抑制窗口内重复触发）
  - 未设定层级1
  - 未设定发送人员
  - 注：「子系统 BYPASS，仅记录」属于**成功建立但 LogOnly**，不是无效警报，不计入本表。
- **验收标准**：
  - [ ] 当厂别不存在或停用时触发，系统应返回原有失败结果，并新增 1 条原因为“未设定厂别”的无效警报记录。
  - [ ] 当子系统不存在/停用/未与厂别对应、机台不存在/停用时，分别记录“未设定子系统”“未设定机台”。
  - [ ] 当无匹配设定或绑定事件缺失/停用时，记录“找不到事件”；设定存在但停用时记录“警报设定未启用”。
  - [ ] 当在忽略窗口内重复触发同一四要素时，记录“忽略相同警报”。
  - [ ] 当事件无层级 1 或层级 1 无发送人员时，分别记录“未设定层级1”“未设定发送人员”。
  - [ ] 触发成功（含 BYPASS LogOnly）时不应写入无效警报记录。
  - [ ] 一次失败触发只写 1 条记录，原因取首个未通过的校验（短路，与现行返回顺序一致）。
  - [ ] 入参中不存在于主档的厂别/机台等代码仍按原始入参值留存，不因主档缺失而丢字段或报错。

## REQ-002: 无效警报查询报表（按时间区间等条件）

- **优先级**：P2
- **用户价值**：在统一报表入口按时间区间与四要素/原因检索失败明细。
- **需求描述**：新增一个查询报表，复用现有 `report_defs` + `ReportPage` 条件查询/表格/汇出范式。支持以「资料时间」做时间区间（between，精确到秒，含端点），并支持按厂别代码/名称、子系统代码/名称、机台代码、警报代码、失效原因做文本条件过滤；多条件取交集。结果按资料时间倒序。
- **验收标准**：
  - [ ] 用户从侧栏「查询报表」进入「无效警报查询」，页面提供查询、重新整理、汇出按钮，布局与 AVPA004 一致。
  - [ ] 设定时间区间查询时，仅返回资料时间落在区间（含起止端点）内的记录，倒序排列。
  - [ ] 叠加厂别/子系统/机台/警报代码/原因条件时，结果同时满足所有启用条件，运算符语义（包含/等于/介于等）与现有报表一致。
  - [ ] 未勾选任何有效条件直接查询时的行为见 4.1（默认允许全量，分页展示），不应报错或长时间无响应。
  - [ ] 结果表格支持本地列过滤、排序、分页，页大小候选与其它报表一致。
  - [ ] 区间内无数据时展示空态，且不报错。

## REQ-003: 查询结果 Excel 汇出

- **优先级**：P2
- **用户价值**：供线下分析与留存。
- **需求描述**：复用现有报表汇出端点，导出**当前画面结果**（含已应用的查询条件、列过滤与排序），仅导出该报表声明的列，只读、不改业务数据。
- **验收标准**：
  - [ ] 点击汇出可下载与画面过滤/排序后一致的 Excel。
  - [ ] 未查询即汇出时的可用数据范围与 AVPA004 现有行为一致（空结果或当前已载入结果），不导出无关表数据。
  - [ ] 导出列与表头和报表定义一致，时间列为时间格式。

## REQ-004: 导航与权限可见性

- **优先级**：P2
- **需求描述与验收**：
  - [ ] 在「查询报表」分组新增「无效警报查询」菜单项，仅登录使用者可见，沿用现有导航（后端 `functions` 返回才显示）与权限模型，不新增角色或特殊权限。
  - [ ] 未登录访问报表数据接口应被现有鉴权拦截。

# 4. 产品规则

## 4.1 页面与交互

| 位置 / 入口 | 用户操作 | 系统反馈 | 备注 |
|-------------|----------|----------|------|
| 侧栏「查询报表」→「无效警报查询」 | 进入页面 | 显示工具栏（查询/重新整理/汇出）与空表格，提示“请执行查询” | 与 AVPA004 同构；菜单仅后端 functions 返回时显示 |
| 条件弹窗 | 勾选「资料时间」，选「介于」并填起止（精确到秒） | 勾选后运算符与时间输入可用；未勾选置灰 | 复用 RecordDialog wide + 现有条件控件 |
| 条件弹窗 | 勾选原因/四要素文本条件并填值 | 多条件同时生效（交集） | 运算符沿用 textOps/dateOps |
| 查询按钮 | 提交条件 | 表格按资料时间倒序展示；显示条数 | 失败原因以中文原文展示 |
| 重新整理 | 按当前条件重查 | 刷新结果 | |
| 汇出 | 导出当前画面结果 | 下载 Excel | 复用 /reports/{code}/export |
| 空态 | 区间无记录 | 表格空态文案 | 复用 DataGrid 空态 |

默认查询口径：与 AVPA004「警报处理查询」一致，**不强制至少一个条件**（`ATLEAST_ONE_CONDITION=N`），未加条件时返回记录并由分页兜底（默认每页 20，最大页大小沿用 DataGrid 候选）。待确认项 Q1 可据此回切为“必须选择时间区间”。

## 4.2 字段与校验

| 字段 | 类型 | 必填 | 默认值 | 校验规则 | 展示 / 使用位置 |
|------|------|------|--------|----------|-----------------|
| INVALID_ID（识别码） | text | 系统生成 | 序列 | 唯一，系统生成，规则同其它主键 | 列（可不在默认条件） |
| CREATE_DT（资料时间） | date | 否 | — | 合法日期时间，精确到秒；区间起≤止 | 主查询条件 + 列，倒序排序键 |
| FACTORY_ID / FACTORY_NAME（厂别代码/名称） | text | 否 | 入参原值 | 按入参留存；主档缺失时名称可为空 | 条件 + 列 |
| SUB_SYS_ID / SUB_SYS_NAME（子系统代码/名称） | text | 否 | 入参原值 | 同上 | 条件 + 列 |
| EQP_ID（机台代码） | text | 否 | 入参原值 | 按入参留存，可为空 | 条件 + 列 |
| ALARM_INFO_ID（警报代码） | text | 否 | 入参原值 | 按入参留存，可为空 | 条件 + 列 |
| TITLE（警报标题） | text | 否 | 入参 | 可为空 | 列 |
| REASON（失效原因） | text | 是 | — | 取枚举中文文案之一，与触发 message 一致 | 条件（可包含/等于）+ 列 |
| RECEIVE_TYPE（资料取得方式） | text | 是 | Mock/Test | 与有效警报表口径一致 | 列 |
| SOURCE_TYPE（来源类型） | text | 是 | Test | 与有效警报一致（演示均为测试触发） | 列（默认可不展示） |

> 字段名为产品契约建议，最终以技术设计结合 `enrich` 关联（厂别/子系统/机台 join 出名称）落地；不影响行为口径。对于主档已缺失的失效记录，名称允许为空、代码保留入参值。

## 4.3 状态与流转

无业务状态流转。无效警报记录为一次性、只读、不可变；无 ACK / 完成 / 升级等状态。

## 4.4 接口或数据契约

| 契约对象 | 变化内容 | 是否兼容 | 关联需求 |
|----------|----------|----------|----------|
| 触发流程 `POST /api/alarms/test` | 失败分支新增“写无效警报记录”副作用；响应体与 422 状态码不变 | 是 | REQ-001 |
| 新增无效警报记录集合 | 新增一类只读写模型记录（含上文字段、时间戳、原因） | 是（新增，不改旧表） | REQ-001 |
| 报表定义 `report_defs` / 导航 `functions` | 新增 1 个报表定义与其菜单项 | 是（新增） | REQ-002/004 |
| `GET /api/report-defs/{code}`、`POST /api/reports/{code}/query`、`POST /api/reports/{code}/export` | 在现有白名单/分发中接纳新报表 code，复用既有条件与汇出契约 | 是（扩展现有接口） | REQ-002/003 |

报表 code 与命名建议：`AVPA014`「无效警报查询」（接 AVPA013 之后；最终编码与是否沿用历史代码由技术设计/导航规划确认，见 Q2）。请求/响应包裹与字段命名风格沿用现有报表（`{ok,rows,columns,total,lastUpdate}`、条件 `{enabled,operator,value,from,to}`）。

# 5. 约束与风险

## 5.1 非功能要求

| 类别 | 要求 | 验收方法 |
|------|------|----------|
| 兼容 | 不改变触发成功/失败语义、状态码与既有报表行为；旧库（checked-mvp-1 之前）不迁移 | 回归现有警报/报表 E2E；旧数据不报错、新表为空 |
| 性能 | 写记录纳入现有单事务快照，不引入额外连接；查询默认分页，全量查询不造成明显卡顿 | 接口测试 + 大数据量分页手工验证 |
| 可用 | 落库失败不得让“失败触发”返回成功；写记录异常按现有事务回滚并保持 422 语义 | 单测/集成测试 |
| 安全/权限 | 仅登录可见可查；记录不含密码、邮箱凭据等敏感信息 | 鉴权 E2E + 数据检查 |
| 可观测 | 失效原因中文文案稳定，可用于检索与统计 | 接口断言原因枚举 |

## 5.2 风险与待确认

| 类型 | 描述 | 影响 | 处理方式 |
|------|------|------|----------|
| 风险 | 旧版明确删除过“无效告警报表”，本需求是在新架构恢复 | 范围若蔓延易夹带其它被删模块 | Spec 已限定仅无效警报查询，不恢复其它模块（1.3） |
| 风险 | 失效发生在主档不存在时，join 不出名称 | 名称列可能为空 | 代码保留入参原值，名称允许为空（4.2） |
| 待确认 | Q1：未加任何条件是否允许全量查询 | 影响数据量与默认交互 | 默认对齐 AVPA004 允许全量+分页；如需强制时间区间，改 `ATLEAST_ONE_CONDITION` 即可，技术路径不变 |
| 待确认 | Q2：报表 code/命名（建议 AVPA014「无效警报查询」）与默认展示列 | 仅影响配置与文案 | 技术设计阶段按导航编码惯例确认；不改变架构 |
| 待确认 | Q3：是否需要保留原始入参标题/内容、来源 IP 等审计字段 | 影响列集合 | 默认保留标题/内容/取得方式，不留 IP；可参数级增减 |

# 6. 验收清单

- [x] 核心用户场景（失败触发→落库→按时间区间查询→看原因→汇出）已覆盖。
- [x] 每条功能需求都有可判定的验收标准。
- [x] 非目标、兼容性（不改触发语义/不迁移旧库）和风险已说明。
- [x] 需设计或研发判断项（全量查询口径、报表 code、审计字段）已标记为待确认 Q1–Q3，且均为参数级、不改变技术路径。

## 6.1 建议的客观验证点（供技术设计 / 测试节点细化）

- 后端单测：逐类失效原因触发后写且仅写 1 条记录、字段与原因正确；成功/BYPASS 不写。
- 报表条件单测：时间区间含端点、多条件交集、倒序、空态（可复用 `ReportConditionsTest` 范式）。
- 接口/E2E：登录后经查询端点按区间取回记录、未登录 401；汇出文件列正确。
- 前端：菜单仅在 functions 返回时出现；条件弹窗、表格、汇出与现有报表一致。
